# 카드깡 알바생의 하루 VR – 시스템 설계서 (v1, 검토용)

기준 문서: `카드깡_알바생의_하루_VR_컨셉기획서_v2.md`, `카드아트_Gemini_프롬프트_가이드.md`
환경: Unity 6000.3.15f1 · URP 17.3 · XRI 3.5.1 · OpenXR (Meta Quest)
목표: **5일 안에 완성하면서도, 수치·카드·일수를 코드 수정 없이 바꿀 수 있는 구조**

## 1. 설계 원칙 (유지보수 기준)

| 원칙 | 적용 |
| --- | --- |
| 수치는 코드에 쓰지 않는다 | 확률·가격·알바비·일수·손님 수·랭크 기준은 전부 ScriptableObject(SO) 설정 파일로 분리. 기획서 8장의 "줄이는 순서"(7일→3일, 청소 3종→2종, 판매 끄기)가 **데이터 수정만으로** 되게 함 |
| 규칙(로직)과 VR 표현(뷰)을 나눈다 | 확률 판정·정산·점수·판매 판정은 MonoBehaviour가 아닌 순수 C# 클래스. XRI 오브젝트는 "입력을 받아 로직에 전달하고 결과를 보여주기"만 담당 → 헤드셋 없이 EditMode 테스트 가능 |
| 바뀔 가능성이 큰 곳만 인터페이스로 | 팩 개봉 방식(찢기 ↔ 버튼, 리스크 문서에 대체안 명시), 난수(디버그 강제 등급·테스트 시드) 두 곳만 추상화. 그 외는 단순 클래스 |
| 카드 ID는 문자열로 고정 | 아트 가이드의 ID(`F-N1`, `SN-L` …)를 그대로 데이터 키로 사용. 리스트 순서·enum 인덱스에 의존하지 않음 |
| 데이터는 검증된다 | 확률 합계, 카드 50장 구성(등급별 17/12/7/7/7), 아트 누락을 에디터 메뉴 한 번으로 검사 |
| 기획서 수치 = 테스트 기준값 | 기획서 5-3의 확률표(③ "한 팩에서 이 등급 이상")를 단위 테스트의 기대값으로 사용. 수치를 바꾸면 테스트가 바로 알려줌 |

과설계를 피하기 위해 **하지 않는 것**: DI 프레임워크, 범용 이벤트 버스 SO, 세이브 시스템(한 판 25~30분, 저장 없음), 네트워크.

## 3. 전체 구조

```text
                 ┌──────────────── 설정 (SO, 읽기 전용) ────────────────┐
                 │ CardDatabase · RarityTable · PackOddsConfig          │
                 │ EconomyConfig · CampaignConfig(일차별) · ScoreConfig │
                 └──────────────────────────┬───────────────────────────┘
                                            │ 참조
┌─ GameContext (씬 유일 진입점) ─────────────▼──────────────────────────────┐
│  Configs · GameSession(상태) · GameEvents · IRandomSource                 │
│  서비스: PackRoller · EconomyRules · SalesRules · ScoreRules ·            │
│          PopularElementSchedule                                           │
└───────────────┬───────────────────────────────────────┬───────────────────┘
                │ 상태 전환                              │ 이벤트 구독/명령
        ┌───────▼────────┐                     ┌────────▼───────────────────┐
        │ GameFlow       │                     │ 뷰 / XRI 컴포넌트           │
        │ (페이즈 상태기계)│                     │ PackView · CardView ·      │
        │ Title → Intro →│◄── 완료 신호 ────── │ BinderView · SalesDisplay ·│
        │ Business →     │                     │ Register(Poke) · Cleanup · │
        │ Settlement →   │                     │ CustomerAgent · UI · Tutor │
        │ AfterHours →   │                     └────────────────────────────┘
        │ DayEnd → Final │
        └────────────────┘
```

- **GameContext**: 씬에 하나 있는 MonoBehaviour. 설정 SO를 인스펙터로 받고, 순수 C# 서비스와 `GameSession`을 생성해 보관. 유일한 싱글톤.
- **GameSession**: 한 판의 모든 상태(일차, 재화, 보유 카드, 진열 카드, 당일 장부, 통계). 순수 C#. 새 게임 = `new GameSession()`.
- **GameEvents**: GameContext가 소유하는 C# event 모음 (`MoneyChanged`, `CardObtained`, `CustomerServed`, `CleanupSpawned/Completed`, `PhaseChanged` …). static을 쓰지 않아 "Enter Play Mode 옵션(도메인 리로드 끔)"에서도 구독이 남지 않음.
- **IRandomSource**: `System.Random` 래퍼. 테스트는 고정 시드, 디버그는 "다음 결과 강제" 래퍼로 교체.

## 4. 데이터 설계

### 4-1. 카드 데이터: CSV → SO 자동 생성

카드 50장을 SO 50개로 손으로 만들면 수정·검수가 어렵습니다. **`02. Data/cards.csv`를 원본으로 두고, 에디터 메뉴로 SO를 생성/갱신**합니다.

```csv
id,kind,element,rarity,name,description,charArt,bgArt,fgArt
F-N1,Slime,Fire,Normal,불씨 슬라임,"...",F_N1_char,BG_F_W,
F-SR,Slime,Fire,SuperRare,화염 소용돌이 슬라임,"...",F_SR_char,F_SR_bg,
FD-L,Field,None,Legendary,슬라임 성지,"...",,FD_L_bg,FD_L_fg
SN-R,Snack,None,Rare,꿀방울 쿠키,"...",SN_R_char,BG_N_W,
```

- 임포터가 아트 파일 이름 규칙(`-`→`_`)으로 스프라이트를 자동 연결. 누락 시 경고.
- `CardData`(SO, 기존 클래스 유지): `id, kind, element, rarity, displayName, description, basePrice, character, background, foreground`
- **기준가·손님 구매 확률의 원본은 등급(RarityTable).** `CardData.basePrice`는 표시용 사본으로 CSV 임포트 때 RarityTable에서 채우고, 검증기가 불일치를 잡음. 기획서상 같은 등급은 값이 같으므로 50곳에 중복 입력하지 않음. (기획서 5-7의 "카드 ID별 기준가" 항목은 등급에서 파생)
- `CardDatabase`(SO): 카드 목록 + `Get(id)`, `GetByRarity(rarity)` 캐시.

### 4-2. 설정 SO 목록

| SO | 내용 | 기획서 근거 |
| --- | --- | --- |
| `RarityTable` | 등급별 기준가, 손님 구매 확률, 대표색, 프레임 머티리얼, 개봉 효과음, 햅틱 세기, 상자 하이라이트 여부 | 5-4 가격표, 5-6 셰이더 |
| `PackOddsConfig` | 슬롯 3종 확률표, 단서 배율(×1, ×1.5, ×2) · 적용 슬롯(4,5) · 적용 최소 등급(SR), 특수 팩(갓팩 0.2% · 내부 분포 U85/L15, 레전더리 확정 1.0%), 선반 단서 배치 비율(75/20/5) | 5-2, 5-3 |
| `EconomyConfig` | 팩 10, 상자 90, 기본급 40, 청소 +5/−3, 수수료 10%, 인기 속성 ×1.5 · 주기 2일, 진열 4칸, 판매가 최소 1 | 5-5 |
| `CampaignConfig` | 일차 목록(DayEntry): 영업 시간, 손님 수 범위, 활성 청소 종류, 그날 튜토리얼 단계 | 5-1, 5-9, 8장 축소안 |
| `ScoreConfig` | 도감 1종당 점수(10), 랭크 기준(S 4000 / A 3400 / B 2400), 엔딩 문구 | 5-8 |
| `TutorialSequence` | 단계 목록: 트리거 이벤트, 하이라이트 대상 키, 사장님 대사 | 5-9 |

**단서 확률은 표로 저장하지 않고 규칙으로 계산**합니다. 기본 슬롯표 + 배율만 저장하고 런타임에 "SR 이상 ×배율 → 남은 확률을 노말:레어 비율로 재분배"합니다. 기획서 ②표와 일치함을 검산했습니다(예: 단서 1종 5번 슬롯 = 0/49/37.5/12.6/0.9, 단서 2종 4번 슬롯 = 25.9/50.1/21.4/2.4/0.2). 구현 후 테스트로 고정합니다. 기본 확률만 고치면 단서 확률이 자동으로 따라옵니다.

### 4-3. enum

```csharp
public enum Rarity   { Normal = 0, Rare = 1, SuperRare = 2, Unique = 3, Legendary = 4 }
public enum Element  { None = 0, Fire = 1, Water = 2, Earth = 3, Air = 4, Neutral = 5 }
public enum CardKind { Slime = 0, Field = 1, Snack = 2 }
[Flags] public enum PackClue { None = 0, FoldedTop = 1, FlippedBack = 2 }
```

값을 명시해 직렬화가 순서 변경에 깨지지 않게 합니다. ("무속성" 슬라임 = `Neutral`, 필드·간식 = `None`으로 구분 → 인기 속성 판정이 단순해짐)

## 5. 핵심 로직 (순수 C#)

| 클래스 | 책임 | 입력 → 출력 |
| --- | --- | --- |
| `PackRoller` | 팩 1개 판정 | `(clue, isBoxPack)` → `PackResult { CardData[5], SpecialType }` |
| `EconomyRules` | 판매 수령액, 일일 정산 | `SellPrice(card, popular)` = `max(1, floor(base × mult × 0.9))` / `Settle(DayLedger)` |
| `SalesRules` | 손님의 진열 카드 구매 판정 | `(진열 목록, rng)` → 산 카드 또는 "가게 재고" |
| `PopularElementSchedule` | 일차 → 인기 속성 | 7일치를 게임 시작 시 미리 뽑아 둠(재현·디버그 용이) |
| `ScoreRules` | 최종 점수·랭크 | `GameSession` → `FinalResult` |
| `ShelfGenerator` | 선반 팩의 단서 배치 | `(칸 수, rng)` → `PackClue[]` |

`PackRoller` 판정 순서 (명확화 필요 항목 → 9장 Q7):
1. 갓팩(0.2%) 판정 → 맞으면 5장 모두 U85/L15
2. 아니면 레전더리 확정(1.0%) 판정 → 5번 슬롯 레전더리, 1~4번 일반
3. 아니면 슬롯별 판정(단서 보정은 단일 팩 4·5번만)
4. 등급이 정해지면 그 등급 카드 중 균등 추첨

**상태 모델 (`GameSession`)**

```text
GameSession
  Day, Phase
  Wallet            Money, 변경 이벤트
  Collection        카드ID → 보유 장수, 최초 획득 여부(도감)
  SalesDisplay      진열 카드 ID 최대 4장
  DayLedger         기본급, 청소 보너스/감점 건수, 판매 내역(카드, 수령액, 수수료)
  Stats             개봉 팩 수, 최고가 카드, 갓팩/확정팩 횟수
  FreePackAvailable 오늘 무료 팩 사용 여부
```

카드는 **데이터로는 "ID + 장수"만 보관**합니다. 바인더 칸/중복 상자는 이 데이터를 그리는 뷰일 뿐이라, 물리 카드 오브젝트 수가 늘지 않습니다.

## 6. 게임 흐름 (페이즈 상태기계)

`GameFlow`가 `IGamePhase { Enter(); Tick(dt); Exit(); }` 구현체를 전환합니다. 페이즈마다 파일 하나라 흐름 수정이 국소적입니다.

| 페이즈 | 하는 일 | 다음으로 가는 조건 |
| --- | --- | --- |
| `TitlePhase` | 타이틀 UI(Ray), 크레딧 | 시작 버튼 |
| `IntroPhase` (1일차만) | 사장님 첫 팩 → 개봉 → 바인더 안내 → 업무 소개 | 튜토리얼 완료 |
| `BusinessPhase` | 타이머, 손님 스폰 스케줄, 결제, 청소 생성 | 아래 Q1 규칙 |
| `SettlementPhase` | 장부 정산 → 재화 반영 → 정산 UI | 확인 버튼 |
| `AfterHoursPhase` | 무료 팩 · 구매 · 개봉 · 진열 등록 · 바인더 | "퇴근" 버튼 (Q4) |
| `DayEndPhase` | 미판매 진열 카드 반환, 선반 재배치, 일차 +1 | 자동 |
| `FinalPhase` | 최종 점수·랭크·엔딩 | 처음으로 버튼 |

**일시정지**: 튜토리얼 정지는 `Time.timeScale = 0`을 쓰지 않습니다(물리 기반 Grab·Socket이 멈춰 VR 조작이 깨짐). 대신 `GameFlow.IsPaused` 플래그로 영업 타이머·손님 AI만 멈춥니다. Quest 헤드셋을 벗었을 때(`OnApplicationPause`)도 같은 플래그를 씁니다.

## 7. VR 표현 · 상호작용 계층

### 7-1. XRI 사용 정리

| 대상 | XRI 컴포넌트 | 비고 |
| --- | --- | --- |
| 팩, 카드, 쓰레기, 걸레, 흐트러진 팩 | XRGrabInteractable | |
| 바인더, 판매 진열대 4칸, 쓰레기통, 진열대 칸 | XRSocketInteractor | **Interaction Layer**로 받을 수 있는 대상 제한 |
| 결제 버튼, 상자 개봉 버튼, 퇴근 버튼 | XRPokeInteractor + 버튼 | |
| 타이틀·정산·요약·최종 UI | Ray + TrackedDeviceGraphicRaycaster | |

**Interaction Layer 고정 목록** (ProjectSettings에 한 번 정의, 코드에서는 상수 클래스로 참조)
`Default, Pack, Card, Trash, Rag, UI`

### 7-2. 팩 개봉: 방식 교체 가능 구조

```text
PackView (Grab)  ──► IPackOpenMethod ──► PackOpened 이벤트 ──► CardRevealSequence
                       ├ TearGestureOpen  (두 손 잡고 당기기, 거리 임계값)
                       └ ButtonOpen       (팩 상단 Poke/트리거, 대체안)
```

찢기 구현이 늦어지면 프리팹의 컴포넌트만 바꿉니다.

2일차 구현: `ActivatePackOpen`(팩을 든 채 트리거)이 먼저 들어가 있고, `TearGestureOpen`은 같은 `IPackOpenMethod`로 추가합니다. 카드는 **개봉 즉시 보유 목록(도감 포함)에 들어갑니다**(`PackOpeningService`). 카운터 위 물리 카드(`CardRevealer`)는 보여주기용이라, 떨어뜨리거나 다음 날로 넘어가도 카드를 잃지 않습니다. 판정(`PackRoller`)은 **개봉 시점**에 호출합니다(선반에 놓인 순간 결과가 정해지지 않음 → 디버그 강제와 충돌 없음).

### 7-3. 카드 표시와 오브젝트 수

- `CardView` 프리팹 1종이 `CardData` + `RarityTable`을 받아 일러스트·프레임·셰이더를 세팅. 등급별 머티리얼은 5개 공유, 일러스트 텍스처만 교체.
- 개봉 카드 5장은 **오브젝트 풀**에서 꺼내고, 바인더/진열대/중복 상자로 들어가면 데이터에 반영 후 풀로 반환.
- 바인더 50칸 전부에 소켓을 두지 않습니다. ✅ 확정: **바인더 표지(소켓 1개)에 카드를 꽂으면 해당 칸에 자동 배치**, 바인더 페이지는 10칸 × 5페이지를 넘겨 보는 표시 전용. (소켓 50개는 무겁고 꽂을 칸을 찾는 조작도 번거로움)
- 상자 개봉 50장은 물리 카드를 만들지 않고 연출용 카드 몇 장 + 요약 UI로 처리.

### 7-4. 업무 (손님 · 결제 · 청소)

- `CustomerAgent`: NavMesh 이동(ai.navigation 설치됨) + 상태 `Enter → Browse → Queue → WaitPay → Leave`. 무엇을 살지는 `SalesRules`가 결정, 에이전트는 이동·애니메이션만.
- `CashRegister`: Poke 버튼 → 맨 앞 손님 결제 → 장부 기록.
- `CleanupSpot` 추상 클래스 + `TrashSpot`, `SmudgeSpot`, `MessyPackSpot`. 공통 이벤트 `Completed`. `CleanupDirector`가 손님 퇴장 시 `CampaignConfig`의 그날 활성 종류 중 하나를 생성, 영업 종료 시 미완료 수를 장부에 기록. 청소 종류 축소 = 데이터 수정.
- `SmudgeSpot`: 걸레 콜라이더가 얼룩 위에서 이동한 누적 거리로 진행도 계산(셰이더 알파 감소).

### 7-5. 튜토리얼

`TutorialDirector`가 `GameEvents`를 구독하고, `TutorialSequence`의 "처음 발생한 이벤트"에 반응해 정지 → 하이라이트 → 사장님 대사 → 확인 시 재개. 하이라이트 대상은 씬 오브젝트의 `HighlightTarget(key)` 컴포넌트로 찾습니다(이름 검색 금지).

### 7-6. 선반 팩 고르기와 방향 유지 (Q6 확정)

모바일 포켓몬 카드 게임의 팩 고르기처럼, **플레이어가 뒤집어 둔 팩은 그 방향 그대로 남습니다.** 마음에 드는 팩을 뒤집어 "찜"해 두고 나중에 고르는 경험을 줍니다.

| 상태 | 위치 | 정해지는 때 | 확률 영향 |
| --- | --- | --- | --- |
| `Clue` (접힘 · 뒤집힘 플래그) | `PackItem` 데이터 | 선반 생성 시 (`ShelfGenerator`) | **있음** – 개봉 시 `PackRoller`에 전달 |
| `IsFaceDown` (현재 앞/뒤) | `PackView` 표시 상태 | 생성 시 초기값(뒤집힘 단서면 뒷면) → 이후 플레이어가 바꿈 | 없음 |

- **확률은 생성 시 고정된 플래그만 봅니다.** 앞면인 팩을 뒤집어도 확률이 오르지 않고, 단서 팩을 앞면으로 돌려도 확률이 내려가지 않습니다.
- 그 결과 "처음부터 뒤집혀 있던 팩"과 "내가 뒤집어 둔 팩"을 기억으로 구분하는 것이 플레이어 몫이 됩니다. 의도된 재미로 봅니다.
- 접힘 단서는 모델 변형이라 앞/뒤 어느 쪽에서도 보입니다.
- **선반 슬롯 스냅**: 슬롯(`ShelfSlotSocket`)은 팩을 놓는 순간 팩 앞면 방향을 판정해 **앞면 자세 / 뒷면 자세 두 가지 중 하나**로 스냅합니다. 그래서 정돈된 모습을 유지하면서 방향도 보존됩니다. 다른 빈 슬롯에 놓아도 같은 규칙이 적용됩니다.
- **놓친 팩**: 선반 밖(바닥 등)에 놓인 팩은 3초 뒤 원래 슬롯으로 돌아가며, 방향은 유지합니다. 팩을 잃어버려서 막히는 일을 막습니다.
- **유지 범위**: 하루 안에서 유지됩니다. 다음 날 아침에는 Q5 규칙대로 선반을 다시 배치하므로 방향이 초기화됩니다.

## 11. 구현 순서 (기획서 9장 일정에 대응)

| 일차 | 시스템 작업 |
| --- | --- |
| 1일차 | 패키지 정리 · Quest 빌드 확인 → 폴더/asmdef → enum·SO 정의 → CSV 임포터·검증기 → GameContext/GameSession/GameFlow 뼈대(페이즈 빈 구현으로 Title→Final 한 바퀴) |
